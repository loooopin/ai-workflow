# ai-workflow-bugfix 修 bug 链路

修 bug 与优化的结构化流程。核心纪律：**先定位后动手，证据先于结论**。

## 任务产物存放

```
{project}/.docs/PROCESS/{YYYYMMDD}-{slug}/
├── state.md          # 任务状态（模板见 runtime/templates/state-template.md）
├── 01-symptom.md     # 现象收集
├── 02-evidence.md    # 证据定位与假设清单
├── 03-rootcause.md   # 根因确认
├── 04-fix-summary.md # 修复方案摘要
└── retro.md          # 复盘
```

创建目录时同步更新 `~/workspace/ai-workflow/runtime/tasks/CURRENT`。

## 阶段 0：环境探测

同 ai-workflow-dev：公司仓库则加载 ai-workflow-amar 知识与公司工具能力（日志查询、配置查询）；非公司仓库降级为纯代码+本地日志链路。

## 阶段 1：现象收集

向用户收集（能自动获取的不问人）：

- 现象描述、影响范围、发生频率（必现/偶现/特定条件）
- 首次出现时间（决定查日志的时间窗）
- 可用的复现路径或线上案例（uid/roomId 等关键参数）
- 是否已有临时止血措施

产物：`01-symptom.md`。若信息不足以定位，列出缺口让用户补充，**不要带猜测进入下一步**。

## 阶段 2：证据定位

按顺序执行，每步先展示原始数据再分析：

1. **先读代码链路**：从入口顺着调用链梳理，列出所有可能出问题的检查点及其判断逻辑。严禁不看代码就查数据。
2. **查日志**（公司仓库**必须执行**，不得跳过）：错误日志 + **必须找成功案例做对比**；公司环境走日志查询工具，附时间窗与关键词。
3. **查配置**：怀疑配置相关时查询配置中心，先展示原始配置再分析。
4. **缩小范围**：每轮定位后更新假设清单，标注每个假设的证据等级：
   - 【已证实】有直接证据
   - 【待验证】有间接证据，附验证方法
   - 【推测】无证据，最后才列
5. 禁止表述："根因可能是……"——没证实的只能叫推断。

### ⛔ 验证关卡（进入阶段 3 的前置条件）

**代码分析产出的假设不等于结论。** 进入阶段 3 之前必须满足以下条件，否则**禁止输出根因结论**：

1. **至少一个假设达到【已证实】**：必须有日志、数据或配置的直接证据支撑，纯代码推理不算"已证实"。
2. **公司仓库必须查过日志**：如果阶段 2.2（查日志）尚未执行，不得进入阶段 3。仅凭代码逻辑推导出的假设最多标注【待验证】。
3. **假设清单中无【已证实】项时的处理**：
   - 向用户明确说明"当前所有假设均未验证"
   - 列出各假设及对应的验证方法
   - 请求用户提供验证所需的信息（roomId、uid、时间窗等），或执行验证步骤
   - **不得**输出"最可能的原因是…"之类的结论性表述

> 📌 **反面案例**（来自 retro-20260903-quality-room）：仅凭代码分析推导出"多用户各自停留不满1分钟"的结论并输出给用户，
> 实际日志验证后发现是"单用户 + 重复 JOIN_ROOM 事件导致 Goback 重置"——完全不同的根因。

### 🔄 外部链接/数据源不可用时的降级策略

当用户提供的 tunnel 链接、监控链接或其他外部数据源无法访问时：

1. **不得放弃数据获取**。必须尝试以下替代方案：
   - 从 Kibana 日志中用**时间窗 + traceId/roomId/userId** 还原请求数据
   - 从 Aspect 日志中提取 `[RequestOut] [External/Internal] [Final]` 获取完整的请求参数和响应
   - 请求用户提供截图、响应 JSON 或关键参数
2. **记录不可用原因**（HTTP 状态码、超时等），便于后续排查。

## 阶段 3：根因确认

- 根因必须有证据支撑（日志/代码/数据三选一），写明证据出处。
- 区分**直接原因**与**根本原因**（如：直接原因是空指针，根本原因是上游漏传字段）。
- 向用户确认根因结论后才进入修复。

## 阶段 4：修复

1. 给出修复方案（最小改动优先；如需重构必须说明理由并评估影响面）。
2. 公司仓库遵守公司编码规范（异常、告警、日志风格见 ai-workflow-amar）。
3. 若修复涉及其他团队模块 → 红旗停表，询问用户是否由本人改或通知对方。

## 阶段 5：回归验证

1. 针对根因编写/补充单元测试（红-绿循环：先写能复现 bug 的失败测试 → 确认测试红 → 应用修复 → 确认测试绿）。
2. 测试写在公共接口边界（seam），不要 mock 内部实现——确保将来重构不会让回归测试误报。
3. 列出回归影响面：此修复可能影响的其他调用方，逐一确认。
4. 公司仓库：确认是否需要同步检查配置/数据订正。

## 阶段 6：复盘（强制）

调用 ai-workflow-retro：

- 记录：现象、根因、修复方式、耗时
- 必答三问：为什么测试没覆盖到？为什么监控没发现？同类问题如何预防？
- 用户填写"本次 AI 的问题"（如有）

## 快捷模式

- `ai-workflow-bugfix --hotfix`：跳过完整复盘，只写一行记录进 retro 的 hotfix 清单，事后补全。
