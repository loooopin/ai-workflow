# ai-workflow-dev 功能开发主链路

端到端功能开发编排器。

## 核心原则

- **务实优先**：流程服务于交付，不是反过来。过程文档的数量应与任务规模匹配。
- **确认点必须有价值**：每个确认点都应让用户做出实质判断（如确认需求理解、选择设计方案、审核变更范围），禁止纯走流程的空确认（如"我要进入下一阶段了，确认？"）。
- **禁止向用户展示内部评分**：模糊度评分等内部机制用于 Agent 自身判断，不对用户输出。
- **对外文档极简**：输出给其他团队（如客户端）的接口文档，只写变更字段名、类型、取值说明。不暴露服务端类名/实现逻辑，不列无变更的接口，不教对方怎么做。格式用纯文本缩进，不用 markdown。

## 任务分流（阶段 0 后立即判断）

| 通道 | 条件 | 走哪些阶段 | 确认点 |
|------|------|-----------|--------|
| 快速 | ≤5 文件，无架构影响，需求明确 | 澄清(可合并到录入) → 编码 → 自检 |
| 标准 | 6-15 文件，或有跨模块影响 | 全部，但设计/拆解可轻量 |
| 重型 | >15 文件，或架构变更 | 全部，设计需独立评审 |

分流结果告知用户，用户可随时升级/降级。各通道的确认点数量不同，但每个确认点都必须让用户做出实质判断。

## 任务产物存放

**业务相关产物**（需求、设计、ledger 等）放在当前项目目录下：
```
{project}/.docs/PROCESS/{YYYYMMDD}-{slug}/
├── state.md
├── 01-requirement.md
├── 02-clarify.md
├── 03-design.md
├── 04-tasks.md
├── ledger.md
└── retro.md
```

**工作流引擎状态**（仅跨项目调度用）放在全局目录：
```
~/workspace/ai-workflow/runtime/tasks/CURRENT   # 当前活跃任务的项目路径+任务目录
```

CURRENT 内容格式：`{project_path}/.docs/PROCESS/{task_dir}`

## 阶段 0：环境与状态恢复

1. **公司环境探测**：检查当前项目是否为公司仓库（特征：pom.xml 含 `com.immomo` groupId，或目录名为 `ultron-*`）。
   - 是公司仓库 → 读取 ai-workflow-amar skill 并加载公司知识。
   - 非公司仓库 → 仅使用通用层。
2. **状态恢复**：读取 `~/workspace/ai-workflow/runtime/tasks/CURRENT`。
   - 存在且任务未完结 → 恢复上下文，从上次停留的阶段继续。
   - 上下文被压缩后重新开始工作时，**必须**先做本步骤，严禁凭摘要记忆续做。
3. **任务分流**：根据需求描述初步判断改动规模，选择通道。

## 阶段 1：需求录入

1. 输入形式：PRD 文档（PDF/Markdown，读取后结构化提取）、用户口述、Issue 链接。
2. 提取要素：背景、目标、功能点列表、非功能要求、验收标准、涉及的系统/仓库。
3. 显式列出**文档中不清晰的点**，作为下一阶段澄清的输入。
4. 产物：`01-requirement.md`（快速通道可省略独立文件，直接进澄清）。

## 阶段 2：需求澄清

轻量苏格拉底循环，目标是把模糊需求变成可设计的规格，**不是无限追问**：

1. 内部评估 5 个维度（意图、范围、非目标、约束、验收标准），**不对用户展示评分过程**。
2. 能从代码/上下文推断的答案不问用户——先自己读代码确认，确实无法判断才问。
3. 每轮只问**一个**最弱维度的问题，优先用结构化选项（让用户选而不是让用户写）。
4. 默认上限 5 轮；充分清晰或用户说"清楚了"即收敛。
5. 产物：`02-clarify.md`。
6. 快速通道：录入+澄清可合并为一轮交互，一次性出结构化选项让用户确认。

## 阶段 3：设计评审

产出设计文档（变更文件清单、数据流、兼容性分析）。产物 `03-design.md`。

- **快速通道**：跳过，直接编码。
- **标准通道**：轻量设计，不启动独立评审。
- **重型通道**：调用 ai-workflow-design-review skill，独立子 Agent 对抗性评审。

## 阶段 4：任务拆解与工时预估

- **快速/标准通道**：用 TODO 列表代替独立文件，不做工时预估。
- **重型通道**：调用 ai-workflow-estimate skill，产物 `04-tasks.md`。

## 阶段 5：编码实现

1. 将子任务转为 TODO 列表，逐项执行。
2. **ledger 纪律**：在任务目录维护 `ledger.md`，每完成一个子任务追加一行：做了什么、改了哪些文件、验证方式。
3. **红旗停表**：遇到以下情况立即停止并询问用户，禁止自行绕路：
   - 设计文档与实际代码结构冲突
   - 需要修改公共组件/其他人负责的模块
   - 需要引入新依赖
   - 同一错误修复尝试失败 2 次
   - 发现需求规格有遗漏（回到阶段 2 补充，而不是自行假设）
4. 公司仓库编码时必须遵守已加载的公司知识（异常处理、日志、告警、工具类选型）。

## 阶段 6：单元测试

1. 为新增/修改的核心逻辑编写单元测试（公司仓库注意：根 pom 默认 skipTests=true，运行测试需显式开启）。
2. 测试覆盖：正常路径、边界、异常分支。
3. 无法单测的部分（如强依赖外部 RPC）明确列出，转为自测 checklist。

## 阶段 7：质量自检门

声明完成前必须全部满足并附**实际证据**（命令输出，不是"应该没问题"）：

- [ ] 所有 TODO 完成
- [ ] 编译通过
- [ ] 测试通过（附运行输出）
- [ ] lint/checkstyle 无新增问题
- [ ] ledger 与实际变更一致（对照 git diff 检查）

## 阶段 8：复盘关卡

调用 ai-workflow-retro skill。用户说"跳过复盘"时允许跳过。

## 快捷模式

- `ai-workflow-dev --light`：强制快速通道。
- `ai-workflow-dev --continue`：直接恢复 CURRENT 任务。
- 任意阶段可说"跳过本阶段"。
