# ai-workflow-dev 功能开发主链路

端到端功能开发编排器。

## 核心原则

- **务实优先**：流程服务于交付，不是反过来。过程文档的数量应与任务规模匹配。
- **确认点必须有价值**：每个确认点都应让用户做出实质判断（如确认需求理解、选择设计方案、审核变更范围），禁止纯走流程的空确认（如"我要进入下一阶段了，确认？"）。
- **禁止向用户展示内部评分**：模糊度评分等内部机制用于 Agent 自身判断，不对用户输出。
- **对外文档极简**：输出给其他团队（如客户端）的接口文档，只写变更字段名、类型、取值说明。不暴露服务端类名/实现逻辑，不列无变更的接口，不教对方怎么做。格式用纯文本缩进，不用 markdown。

## 任务分流（阶段 0 后立即判断）

| 通道 | 条件 | 走哪些阶段 | 确认点 |
|------|------|-----------|--------|
| 快速 | ≤5 文件，无架构影响，需求明确 | 澄清(可合并到录入) → 编码 → 自检 |
| 标准 | 6-15 文件，或有跨模块影响 | 全部，但设计/拆解可轻量 |
| 重型 | >15 文件，或架构变更 | 全部，设计需独立评审 |

分流结果告知用户，用户可随时升级/降级。各通道的确认点数量不同，但每个确认点都必须让用户做出实质判断。

## 任务产物存放

**业务相关产物**（需求、设计、ledger 等）放在当前项目目录下：
```
{project}/.docs/PROCESS/{YYYYMMDD}-{slug}/
├── state.md
├── 01-requirement.md
├── 02-clarify.md
├── 03-design.md
├── 04-tasks.md
├── ledger.md
└── retro.md
```

**工作流引擎状态**（仅跨项目调度用）放在全局目录：
```
~/workspace/ai-workflow/runtime/tasks/CURRENT   # 当前活跃任务的项目路径+任务目录
```

CURRENT 内容格式：`{project_path}/.docs/PROCESS/{task_dir}`

## 阶段 0：环境与状态恢复

1. **公司环境探测**：检查当前项目是否为公司仓库（特征：pom.xml 含 `com.immomo` groupId，或目录名为 `ultron-*`）。
   - 是公司仓库 → 读取 ai-workflow-amar skill 并加载公司知识。
   - 非公司仓库 → 仅使用通用层。
2. **状态恢复**：读取 `~/workspace/ai-workflow/runtime/tasks/CURRENT`。
   - 存在且指向有效任务目录 → 读取该目录下 `state.md`，确认当前阶段和待办摘要。
   - 恢复后**必须向用户确认**：展示"上次停在 X 阶段，待办是 Y，是否从此继续？"
   - 上下文被压缩后重新开始工作时，**必须**先做本步骤，严禁凭摘要记忆续做。
   - state.md 格式见 `runtime/templates/state-template.md`。
3. **任务分流**：根据需求描述初步判断改动规模，选择通道。

## 阶段 1：需求录入

1. 输入形式：PRD 文档（PDF/Markdown，读取后结构化提取）、用户口述、Issue 链接。
2. 提取要素：背景、目标、功能点列表、非功能要求、验收标准、涉及的系统/仓库。
3. 显式列出**文档中不清晰的点**，作为下一阶段澄清的输入。
4. 产物：`01-requirement.md`（快速通道可省略独立文件，直接进澄清）。

## 阶段 2：需求澄清

轻量苏格拉底循环，目标是把模糊需求变成可设计的规格，**不是无限追问**：

1. 内部评估 5 个维度，**不对用户展示评分过程**：
   - **意图**：用户要解决什么问题？目标是否有歧义？
   - **范围**：改动涉及哪些模块/接口/数据？边界在哪？
   - **非目标**：哪些看起来相关但本次不做？
   - **约束**：技术约束（兼容性、性能）、业务约束（上线时间、协同依赖）是否明确？
   - **验收标准**：怎么判断"做完了"？能否写成可测试的条件？
2. **多服务必问项**（涉及 ≥2 个服务/仓库时，必须在本阶段确认，不得带入编码阶段）：
   - **逻辑归属**：核心业务逻辑放在哪个服务？哪些服务只做透传/入口？
   - **是否迁移**：是从现有服务迁移逻辑过来，还是纯新增？
   - **不动的代码**：有没有看似相关但本次不能改的方法/模块？
   - **调用链路**：确认 `客户端 → 入口服务/方法 → 核心逻辑服务/方法 → 下游依赖` 的完整链路
3. 能从代码/上下文推断的答案不问用户——先自己读代码确认，确实无法判断才问。
3. 每轮只问**一个**最弱维度的问题，优先用结构化选项（让用户选而不是让用户写）。
4. 默认上限 5 轮；充分清晰或用户说"清楚了"即收敛。
5. 产物：`02-clarify.md`。
6. 快速通道：录入+澄清可合并为一轮交互，一次性出结构化选项让用户确认。

## 阶段 3：设计评审

产出设计文档（变更文件清单、数据流、兼容性分析）。产物 `03-design.md`。

- **快速通道**：跳过，直接编码。
- **标准通道**：轻量设计，不启动独立评审。
- **重型通道**：调用 ai-workflow-design-review skill，独立子 Agent 对抗性评审。

## 阶段 4：任务拆解与工时预估

- **快速/标准通道**：用 TODO 列表代替独立文件，不做工时预估。
- **重型通道**：调用 ai-workflow-estimate skill，产物 `04-tasks.md`。

## 阶段 5：编码实现

1. 将子任务转为 TODO 列表，逐项执行。
2. **git 分支**：编码开始前确认当前分支。若用户尚未创建功能分支，提醒用户创建（公司仓库按 `feat/{版本}/{功能名}` 惯例，非公司仓库按项目惯例）。Agent 不自行创建分支或提交，除非用户明确要求。
3. **ledger 纪律**：在任务目录维护 `ledger.md`，每完成一个子任务追加一行：做了什么、改了哪些文件、验证方式。
4. **跨服务迁移检查**（涉及从一个服务迁移逻辑到另一个服务时，必须逐项对齐）：
   - **定位老代码**：先找到原服务中完整的实现代码，通读理解全部逻辑后再写新代码
   - **数据源对齐**：新老服务使用的 Redis datasource-name / DB 配置必须一致（如 `relationRankDao` 对应的物理数据源相同）
   - **Redis Key 对齐**：缓存 Key 的生成规则必须与老代码完全一致，否则迁移期间会读不到老缓存
   - **查询参数对齐**：分页大小、偏移量、查询范围等与老代码保持一致
   - **过滤/排序对齐**：隐私过滤、排序规则、阈值逻辑等与老代码保持一致
   - 以上每一项必须通过**读取老代码确认**，不得凭假设编写
5. **同类代码对齐**：新增代码（DAO/Config/Service）前，先在当前项目 grep 同类代码的写法（DAO 粒度、Key 管理方式、Config 默认值处理等），保持风格一致。
6. **红旗停表**：遇到以下情况立即停止并询问用户，禁止自行绕路：
   - 设计文档与实际代码结构冲突
   - 需要修改公共组件/其他人负责的模块
   - 需要引入新依赖
   - 同一错误修复尝试失败 2 次
   - 发现需求规格有遗漏（回到阶段 2 补充，而不是自行假设）
   - **多服务场景中，发现自己即将在"透传服务"里写业务逻辑**（回到澄清阶段确认归属）
7. 公司仓库编码时必须遵守已加载的公司知识（异常处理、日志、告警、工具类选型）。

## 阶段 6：单元测试

1. 为新增/修改的核心逻辑编写单元测试（公司仓库注意：根 pom 默认 skipTests=true，运行测试需显式开启）。
2. 测试覆盖：正常路径、边界、异常分支。
3. 无法单测的部分（如强依赖外部 RPC）明确列出，转为自测 checklist。

**测试边界（seam）原则**：测试只在公共接口边界编写，验证行为而非实现细节。写测试前先确认：这个测试在被测代码重构（不改行为）后还能通过吗？如果不能，说明测在了实现细节上。

**测试反模式（写测试时逐条自查）**：

| 反模式 | 症状 | 正确做法 |
|--------|------|---------|
| 耦合实现 | mock 了私有方法或内部协作类；重构不改行为但测试挂了 | 只 mock 外部依赖（RPC/DB/MQ），通过公共接口断言结果 |
| 同义反复 | 断言用和被测代码相同的逻辑计算期望值（如 `assertEquals(a+b, add(a,b))`） | 期望值必须来自独立来源：已知常量、需求文档、手算结果 |
| 水平切片 | 一口气写完所有测试再写实现，测试验证的是"想象中的行为" | 一个测试→一段实现→验证通过→下一个测试（垂直切片） |

## 阶段 7：质量自检门

**铁律：没跑过的不能说通过。**

声明完成前必须全部满足并附**实际证据**（命令输出，不是"应该没问题"）：

- [ ] 所有 TODO 完成
- [ ] 编译通过（附 `mvn compile` / 对应构建命令输出）
- [ ] 测试通过（附运行输出，含通过数/失败数）
- [ ] lint/checkstyle 无新增问题
- [ ] ledger 与实际变更一致（对照 git diff 检查）

**反合理化表（声明完成前逐条过，命中任何一条则停止声明）**：

| 你脑中的想法 | 现实 |
|-------------|------|
| "应该没问题了" | "应该"不是证据，跑一遍 |
| "改动很小不会出错" | 小改动出 bug 概率不比大改动低 |
| "lint 过了等于编译过了" | lint 不检查编译，两个必须分别跑 |
| "上次跑过了，这次只改了一点" | 上次的结果不是本次的证据 |
| "测试跑太慢，看代码没问题" | 跑不了就列入"无法验证"项，不能假装通过 |
| "Agent 报告成功了" | 子 Agent 的报告要独立验证（看实际输出） |

## 阶段 8：复盘关卡

调用 ai-workflow-retro skill。用户说"跳过复盘"时允许跳过。

## 快捷模式

- `ai-workflow-dev --light`：强制快速通道。
- `ai-workflow-dev --continue`：直接恢复 CURRENT 任务。
- 任意阶段可说"跳过本阶段"。
