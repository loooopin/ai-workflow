# 阶段 2：需求澄清

轻量苏格拉底循环，目标是把模糊需求变成可设计的规格，**不是无限追问**。

## 内部评估维度（不对用户展示评分过程）

1. **意图**：用户要解决什么问题？目标是否有歧义？
2. **范围**：改动涉及哪些模块/接口/数据？边界在哪？
3. **非目标**：哪些看起来相关但本次不做？
4. **约束**：技术约束（兼容性、性能）、业务约束（上线时间、协同依赖）是否明确？
5. **验收标准**：怎么判断"做完了"？能否写成可测试的条件？

## 多服务必问项

涉及 ≥2 个服务/仓库时，**必须在本阶段确认**，不得带入编码阶段：

- **逻辑归属**：核心业务逻辑放在哪个服务？哪些服务只做透传/入口？
- **是否迁移**：是从现有服务迁移逻辑过来，还是纯新增？
- **不动的代码**：有没有看似相关但本次不能改的方法/模块？
- **调用链路**：确认 `客户端 → 入口服务/方法 → 核心逻辑服务/方法 → 下游依赖` 的完整链路

## 澄清纪律

- 能从代码/上下文推断的答案**不问用户**——先自己读代码确认，确实无法判断才问
- 每轮只问**一个**最弱维度的问题，优先用结构化选项（让用户选而不是让用户写）
- 默认上限 5 轮；充分清晰或用户说"清楚了"即收敛
- 快速通道：录入+澄清可合并为一轮交互，一次性出结构化选项让用户确认
