# 阶段 5：编码实现

## 基本流程

1. 将子任务转为 TODO 列表，逐项执行。
2. **git 分支**：编码开始前确认当前分支。若用户尚未创建功能分支，提醒用户创建（公司仓库按 `feat/{版本}/{功能名}` 惯例，非公司仓库按项目惯例）。Agent 不自行创建分支或提交，除非用户明确要求。
3. **ledger 纪律**：在任务目录维护 `ledger.md`，每完成一个子任务追加一行：做了什么、改了哪些文件、验证方式。

## 跨服务迁移检查

涉及从一个服务迁移逻辑到另一个服务时，必须逐项对齐：

- **定位老代码**：先找到原服务中完整的实现代码，通读理解全部逻辑后再写新代码
- **数据源对齐**：新老服务使用的 Redis datasource-name / DB 配置必须一致
- **Redis Key 对齐**：缓存 Key 的生成规则必须与老代码完全一致，否则迁移期间会读不到老缓存
- **查询参数对齐**：分页大小、偏移量、查询范围等与老代码保持一致
- **过滤/排序对齐**：隐私过滤、排序规则、阈值逻辑等与老代码保持一致
- 以上每一项必须通过**读取老代码确认**，不得凭假设编写

## 编码纪律

- **同类代码对齐**：新增代码（DAO/Config/Service）前，先在当前项目 grep 同类代码的写法，保持风格一致
- **模糊技术指令必须澄清**：用户给出模糊的技术指令（如"用 GUAVA"、"换成 XX 模式"）时，**先一句话复述理解并确认**，不得直接按自己的理解实现
- **优化方案先分析后实现**：涉及缓存/性能优化/架构调整时，**先输出数据特征分析**（变化频率、失效路径、预期收益），用户确认方案后再写代码
- 公司仓库编码时必须遵守已加载的公司知识（异常处理、日志、告警、工具类选型）

## 红旗停表 🚩

遇到以下情况**立即停止**并询问用户，禁止自行绕路：

- 设计文档与实际代码结构冲突
- 需要修改公共组件/其他人负责的模块
- 需要引入新依赖
- 同一错误修复尝试失败 2 次
- 发现需求规格有遗漏（回到阶段 2 补充，不自行假设）
- **多服务场景中，发现自己即将在"透传服务"里写业务逻辑**（回到澄清阶段确认归属）
