# ai-workflow-design-review 设计评审

产出设计文档并用独立子 Agent 做对抗性评审，消除"自己审自己"的确认偏差。

## 流程

### 1. 产出设计文档

输入：需求规格（02-clarify.md 或用户提供）。按 `core/templates/design-doc.md` 模板产出，必须包含：

- 目标与非目标
- 至少 2 个候选方案 + 排除理由（防止只给一个方案造成假选择）
- 选定方案的详细设计：数据模型、接口定义、关键流程、涉及的模块/文件
- 兼容性与回滚策略
- 风险清单
- 验收标准（可测试的）

公司仓库：方案必须声明与公司组件规范的符合性（RPC/配置/缓存/MQ/告警选型）。

### 2. 独立评审

启动一个**只读**的独立子 Agent（Task 工具），只给它：设计文档全文 + 需求规格 + 相关代码路径。**不给**设计过程的推理记录。评审 prompt 要求：

1. 找出方案中最薄弱的环节（必须给出，不许说"整体没问题"）
2. 给出最强反对论证：如果你是评审人，你会用什么理由驳回
3. 检查被掩盖的权衡：方案里有没有回避掉的取舍
4. 对照需求规格逐条检查覆盖度
5. 结论三选一：通过 / 有条件通过（列出条件）/ 驳回重做

### 3. 处理评审意见

- 通过 → 直接进入用户批准
- 有条件通过 → 逐条回应：采纳并修改文档，或给出不采纳的理由（写入文档"评审记录"节）
- 驳回 → 回到第 1 步重做，最多 2 轮；仍被驳回则把分歧点呈给用户裁决

### 4. 证据纪律

设计文档中的每个关键判断标注证据等级：

- 【已证实】有代码/数据/文档证据，附引用
- 【待验证】合理推断，附验证方法
- 【推测】无证据的猜测，必须显式标注

禁止出现"根因是…可能…"这类矛盾表述。

### 5. 用户批准

向用户展示最终文档 + 评审记录摘要，用户批准后产物定稿为 `03-design.md`。
