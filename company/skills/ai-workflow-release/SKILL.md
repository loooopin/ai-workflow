# ai-workflow-release 上线文档生成

分析当前开发分支的变更，产出结构化上线文档（含 checklist）。

## ⚠️ 输出原则（最高优先级）

1. **只列服务端上线操作项和顺序**：文档的唯一目的是告诉服务端上线时"做什么"和"做的顺序"
2. **不列代码描述**：不解释代码逻辑、不描述 DTO 字段变更、不说明 Handler 做了什么、不对比新旧实现
3. **不列客户端/前端关注项**：DTO 新增字段、接口入参变更等客户端适配事项不属于服务端上线操作
4. **不列变更人**：表格中不需要「变更人」列
5. **不列 Hubble 监控**：代码中新增 Hubble client-map 配置不属于上线操作，不检测不列出
6. **Redis 只列需运维操作的**：代码 yml 中新增已有 datasource 配置不算上线操作，仅当需要运维新建 Redis 实例时才列出
7. **互斥依赖必须暴露**：当服务间存在双向新增接口依赖时，不得擅自判断发布顺序，必须列出互斥点并引导用户选择处理方式

## 前置条件

- 当前处于公司仓库（pom.xml 含 `com.immomo`）
- 功能分支已开发完成（至少编译通过）
- 已加载 ai-workflow-amar 公司知识

## 分析流程

### 1. 变更范围采集

自动执行：

1. `git diff master...HEAD --name-only` 获取本分支全部变更文件列表
2. 识别变更涉及的仓库/模块（若为多仓库开发，向用户确认涉及的全部仓库）
3. 逐模块分析变更内容，填充下方各检查项

### 2. 逐项检查（有则列出，无则标"无"）

#### 2.1 多语言

扫描变更中是否新增/修改了多语言 key：
- 搜索代码中新增的 `multilingual` 相关调用
- 检查是否有新的文案 key 需要上传到多语言平台

#### 2.2 版本升级

- **本项目版本**：检查 pom.xml version 是否需要升级（如改了 -api 包的接口/model）
- **依赖版本**：检查 pom.xml 中新引入或升级的 dependency（特别是内部 -api/-wrapper 包）

#### 2.3 盘古（MSE）配置

扫描变更中：
- 新增的 `@MomoConfig` 注解 → 需要在 MSE 配置中心新建 key
- 已有 `@MomoConfig` 但 value 结构变更 → 需要修改线上配置值
- 检查是否有默认值（`defaultVal`），评估首次上线时配置缺失的影响

#### 2.4 网关配置

扫描变更中新增的对外接口：
- `@MoaProvider` 暴露的新接口方法
- 需要对外暴露给客户端/第三方的接口 → 需配置到网关

#### 2.5 定时任务

扫描变更中：
- 新增的定时任务接口（MOA 接口 + TaskLockUtil 模式）
- 需要在调度平台注册 cron 表达式

#### 2.6 MySQL 建表

扫描变更中：
- 新增的 Entity/DAO/Mapper 对应的表
- 检查是否有建表 SQL（若无，生成建表语句供 DBA 审核）

#### 2.7 Kafka Topic

扫描变更中：
- 新增的 `MomoKafkaProducer` 发送目标 topic
- 新增的 `@KafkaMessageListener` 消费 topic
- 新 topic 需要申请创建

#### 2.8 上线顺序

若涉及多个项目/仓库：
- 分析依赖关系（谁的 -api 被谁引用）
- 确定上线顺序（先上 provider 再上 consumer）
- 标注是否需要灰度/分批

### 3. 生成文档

将分析结果按模板输出。用户确认后定稿存入任务目录。

## 与用户的交互

1. 自动分析完成后，展示草稿文档。
2. 用户确认/修改各项内容。
3. 定稿后存入 `{project}/.docs/PROCESS/{task}/release.md`（若在 dev 流程中）或用户指定位置。

## 快捷用法

```
上线文档
```

若当前有活跃的 ai-workflow-dev 任务，自动关联该任务的变更范围；否则基于当前分支与 master 的 diff 分析。
